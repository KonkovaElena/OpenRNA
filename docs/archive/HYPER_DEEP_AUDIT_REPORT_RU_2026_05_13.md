## 1. Что такое OpenRNA и зачем он нужен

OpenRNA — это «мозг» (control plane) для производства персонализированных РНК-вакцин против рака. Процесс выглядит так:

1. **Взятие образцов** — берутся ткани пациента (опухоль + здоровая ткань).
2. **Секвенирование** — определяются мутации ДНК.
3. **Предсказание неоантигенов** — компьютерные модели находят белковые фрагменты, которые иммунная система может «увидеть».
4. **Дизайн конструкта** — выбираются оптимальные РНК-последовательности.
5. **Производство** — вакцина синтезируется в GMP-условиях.
6. **Контроль качества** — проверяется каждый этап.
7. **Одобрение комиссии** — этический комитет подтверждает безопасность.
8. **Введение пациенту** — вакцина вводится, отслеживается иммунный ответ.

**Почему это критически важно:** каждый шаг должен быть полностью прослеживаемым (traceability), защищённым от несанкционированного доступа и соответствовать FDA/EMA регламентам. Ошибка на любом этапе может привести к неправильной вакцине для конкретного пациента.

## 2. Архитектура проекта

### 2.1 Гексагональная архитектура (Ports and Adapters)

Проект использует паттерн «гексагональная архитектура» — это золотой стандарт для медицинских систем. Суть: бизнес-логика (ядро) ничего не знает о базе данных, HTTP, файловой системе. Все взаимодействия идут через «порты» (интерфейсы), а «адаптеры» реализуют технические детали.

**Преимущества для онковакцин:**
- **Замена базы данных** — можно перейти с PostgreSQL на другую СУБД, не меняя бизнес-логику.
- **Тестирование** — можно тестировать всю логику на «фейковой» памяти (in-memory), не поднимая базу.
- **Аудит** — каждое действие оставляет след в аудитной цепочке.

### 2.2 18-состояний жизненного цикла кейса

Каждый пациент (case) проходит через строго определённые состояния:

```
INTAKING → AWAITING_CONSENT → READY_FOR_WORKFLOW → WORKFLOW_REQUESTED → 
WORKFLOW_RUNNING → WORKFLOW_COMPLETED → QC_PASSED → AWAITING_REVIEW → 
APPROVED_FOR_HANDOFF → HANDOFF_PENDING → ...
```

Это конечный автомат (finite-state machine). Переходы между состояниями контролируются — нельзя, например, перейти сразу к «одобрено для выпуска», пропустив контроль качества.

### 2.3 Безопасность и регуляторика

**21 CFR Part 11** (электронные подписи и записи):
- Каждая операция подписывается HMAC-SHA256 (server seal).
- Аудитные события образуют хеш-цепочку (как в блокчейне, но проще): каждое событие ссылается на хеш предыдущего.

**GDPR** (защита данных пациентов):
- Механизм отзыва согласия (consent withdrawal) — пациент может отозвать разрешение, и система блокирует дальнейшую обработку.

**RBAC** (разграничение доступа):
- Роли: OPERATOR, REVIEWER, QUALITY_PERSON, ADMIN, SYSTEM.
- Доступ к кейсам контролируется на уровне отдельного пациента (case-scoped ACL).

## 4. Что нашли: проблемы и риски

### 4.1 Критические проблемы (исправлены)

#### C1. Docker-сборка сломана

**Проблема:** файл `.dockerignore` блокировал `tsconfig.json`, поэтому `docker build` падал на этапе копирования файлов.

**Последствия:** невозможно было собрать контейнер для деплоя.

**Исправление:** убрали `tsconfig.json` из `.dockerignore`.

#### C2. N+1 проблема в списке кейсов

**Проблема:** при запросе списка пациентов (`listCases`) система сначала получала 50 ID, а затем **последовательно** загружала каждого пациента отдельным запросом (~15 дочерних запросов на пациента). Итого **750+ запросов** вместо 1-2.

**Последствия:** при 50 пациентах на странице — задержка в секундах вместо миллисекунд. При росте данных — линейное ухудшение.

**Исправление:** перешли на параллельную загрузку (`Promise.all`). Долгосрочное решение — batched CTE-запрос.

### 4.2 Высокоприоритетные проблемы (исправлены)

#### H1. Метрики (`/metrics`) были открыты без авторизации

**Проблема:** любой сканер Интернета мог получить количество кейсов и их статусы.

**Исправление:** добавили RBAC-проверку `ADMIN_OPERATIONS`.

#### H2. Отсутствие глобальных обработчиков ошибок

**Проблема:** необработанное исключение в фоновой задаче приводило к аварийному завершению процесса Node.js.

**Исправление:** добавили `uncaughtException` и `unhandledRejection` с graceful shutdown.

#### H3. Отсутствие таймаутов HTTP-сервера

**Проблема:** злоумышленник мог открыть соединение и не отправлять данные (Slowloris-атака), исчерпав пул соединений.

**Исправление:** `headersTimeout = 30s`, `requestTimeout = 120s`.

#### H4. Неполный shutdown адаптеров

**Проблема:** при остановке сервера закрывался только основной пул, но не runner и вспомогательные адаптеры.

**Исправление:** добавили `close()` ко всем Postgres-адаптерам и явный порядок закрытия.

#### H5. Отсутствие современных security headers

**Проблема:** не хватало `Cross-Origin-Opener-Policy` и `Cross-Origin-Resource-Policy`, что открывает векторы для Spectre-подобных атак.

**Исправление:** добавлены оба заголовка.

#### H6. Неполнота `.env.example`

**Проблема:** пример конфигурации содержал только 6 переменных из ~20, что приводило к ошибкам при первом запуске.

**Исправление:** синхронизировали с полной схемой `config.ts`.

#### H7-H8. Rate limiter без bound и JWKS cache без eviction

**Проблема:** in-memory rate limiter позволял злоумышленнику исчерпать память, подставляя случайные `x-api-key`. JWKS-кеш мог неограниченно расти при частой ротации ключей.

**Статус:** задокументировано в аудите, исправление запланировано в дорожной карте (Phase 2).

## 8. Заключение

OpenRNA — это **зрелый проект с продуманной архитектурой** и явным пониманием регуляторных требований. Код чистый, тесты надёжные, безопасность продумана на уровне концепции.

**Главные достижения:**
1. Гексагональная архитектура с чётким разделением слоёв.
2. Полная прослеживаемость операций (audit chain с хешами).
3. Механизм согласия пациентов, соответствующий GDPR.
4. 555 тестов с 95 % покрытием строк.

**Главные риски (до исправления):**
1. Сломанная Docker-сборка блокировала деплой.
2. N+1 запросы делали систему непригодной для реальной нагрузки.
3. Открытые метрики и отсутствие глобальных обработчиков ошибок создавали уязвимости.

**Все критические проблемы устранены.** Оставшиеся задачи носят эволюционный характер и позволят довести проект до уровня production-ready системы для клинических испытаний вакцин.
